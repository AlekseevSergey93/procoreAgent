# Требования к историческим данным

Статус: спецификация. Требования относятся к планируемому PostgreSQL-слою.

## Функциональные требования

### FR-1. Ежедневная фиксация

Система должна сохранять состояние каждого активного проекта не менее одного раза в день. Snapshot должен включать доступные модули: schedule, RFIs, submittals, punch, inspections, budget, change orders и daily logs.

### FR-2. Идемпотентность

Для одного проекта и календарной даты допускается ровно один логический snapshot. Повторный запуск обновляет запись и не создаёт дубликат.

### FR-3. Историческое сравнение

Система должна сравнивать выбранный snapshot с предыдущим доступным snapshot и показывать:

- изменение процента выполнения графика;
- новые, закрытые и оставшиеся просроченные items;
- изменение открытых RFI, submittals, punch и deficient inspections;
- изменение revised/projected budget и pending change orders;
- изменение daily-log активности и задержек;
- дату каждого сравниваемого snapshot и их полноту.

### FR-4. Диапазонные тренды

Система должна поддерживать отчёты за диапазон дат: минимум начальное/конечное значение, изменение и список пропущенных дат.

### FR-5. Частичные данные

Если отдельный модуль Procore не загрузился, система должна:

- сохранить доступные данные;
- записать warning;
- отметить snapshot как `partial`;
- не выдавать отсутствие данных за нулевое значение.

### FR-6. Live-режим

Текущие live-инструменты должны продолжать получать актуальные данные из Procore. Недоступность PostgreSQL не должна ломать live-запросы.

### FR-7. Ошибки истории

Исторический запрос при недоступной или немигрированной БД должен завершаться явным диагностическим сообщением, а не пустым успешным ответом.

### FR-8. Безопасность

Credentials PostgreSQL передаются через environment (`DATABASE_URL` или эквивалент), не логируются и не попадают в fixtures, документацию или MCP-ответы.

### FR-9. Отдельный сборщик

Ежедневный сбор должен запускаться отдельным CLI entrypoint, пригодным для системного cron/OpenClaw. MCP stdio-сервер не должен скрыто запускать бесконечный scheduler.

## Нефункциональные требования

- Node.js >= 20 и существующий TypeScript toolchain.
- PostgreSQL с поддержкой `JSONB`, уникальных ограничений и транзакций.
- Миграции воспроизводимы и запускаются в CI/production явно.
- Запись snapshot и его агрегатов атомарна.
- Запрос предыдущего snapshot использует индекс по проекту и дате.
- Timezone и retention настраиваются конфигурацией.
- Ошибки БД логируются в stderr без секретов.
- Тесты не требуют внешнего PostgreSQL по умолчанию: использовать mock/fake pool, а интеграционные тесты маркировать отдельно.

## Критерии приёмки

1. После двух успешных дневных сборов для проекта в БД есть две даты и сравнение показывает изменения.
2. Повторный запуск за ту же дату не увеличивает число snapshots.
3. Сбой одного Procore-модуля создаёт `partial` snapshot с warning.
4. Live MCP-инструменты работают при остановленной PostgreSQL.
5. Исторический MCP-инструмент возвращает понятную ошибку при остановленной PostgreSQL.
6. `npm run typecheck`, `npm run build` и `npm test` проходят.
